> 追加してみましょう。記事はAPIごとに1本、合計2本作成して提出してください。（要件の原文）

## 「読み返せない」の続きから始める

課題9の結論はこうだった。

> LINE には bot が送ったテキストを読み返す API が無い（2026-08-18 に公式 OpenAPI 定義で確認）。
> だから `verify_push.py` は、合格したときにも「確認できないこと」を必ず表示する。

**読み返せないなら、送る前に確かめるしかない。** それが課題10で足すものである。

そして調べてみると、**送る前にしか分からないこと**が実際にあった。

| | |
|---|---|
| `push` は**未友だち・ブロックの相手にも 200 を返す** | 送った後では区別が付かない |
| 友だちかどうかを判定する専用の API は**無い** | `GET /v2/bot/profile/{userId}` の **404** だけが手がかり（ただし 404 は1つのことを言っていない。後述） |

課題8から課題9へ持ち込んだ観点に「**エラーにならない失敗を、実装より先にドキュメントで
確認する**」がある。それをそのまま適用したら、この課題の主題が出てきた。

## なぜ「予定の通知」なのか

課題9の記事に、発展アイデアとしてこう書いた。

> **アイデア2：自治体・店舗の「予定日お知らせ」**
> 実在の事例：松山市が令和6年7月1日から、松山市LINE公式アカウントに
> 「ごみ収集日お知らせ機能」を追加している。

自分で「実用的だ」と調べて書いたものを、次の課題で実装する形にした。
**説明が1行で済む**のも選んだ理由である——「その日の予定が、日付が変わったら LINE に届く」。

| | 値 |
|---|---|
| message ID | `628280397193019597` |
| x-line-request-id | `ceca2881-5734-44c1-9dc6-9bbf0118f09c` |

そして `"20:00" in text` のような部分一致では、**その状態でも通ってしまう**。

照合（`verify_notify.py`）は**14項目すべて一致**した。

### 記録に残ったもの

`results.json` は public リポジトリに入る。**宛先は伏せ字で入る**。

```json
{
  "to_masked": "U8…9a",
  "target_date": "2026-08-21",
  "event_count": 2,
  "all_day_count": 1,
  "usage_before": 5,
  "usage_after": 6,
  "remaining": 195

```

`remaining` が `195` なのは、**送信前ガードが見た時点**の残数だからである
（上限 200 − 送信前の消費 5）。無制限のアカウントならここは `null` になり、
**0 にはならない**。

## 設計

### 送る前に確かめられることは、送る前に確かめる

| 確かめること | 使うもの | 何を防ぐか |
|---|---|---|
| 宛先に届くか | `GET /v2/bot/profile/{userId}` が **404** か | **200 を返すのに届かない**（未友だち・ブロック） |
| 残り通数 | `GET /v2/bot/message/quota` ＋ `/quota/consumption` | 枠切れ |
| 意図したチャネルか | `GET /v2/bot/info` | 課題9から継承 |

### ガードは、カレンダーを読むより前に置く

順番に意味がある。**届かないと分かった時点で止めれば、Google の同意画面すら開かない。**

ガードを後ろに置くと、送らないと決まっている実行でも認可を通すことになる。
「届かない相手のために同意を求めない」という順番を、テストで固定してある
（`test_an_unreachable_destination_does_not_even_read_the_calendar`）。

### 404 を例外にしない

宛先に届かないことは**異常ではない**。送る前に分かる、正常な答えである。

**ただし 404 は1つのことを言っていない。** 公式リファレンスは、
ユーザーIDが存在しない・**プロフィール情報の取得に同意していない**・
友だち追加していない、を並べている。**どれなのかは応答からは区別できない。**
2つ目が効いて、**友だちであっても 404 になりうる**——このガードは
「届くはずの相手を止める」側で間違えうる。止める側の誤りは送ってしまう誤りより
安全だが、**そう書いていなければ利用者は「ブロックされた」と読む**。

例外にすると、呼ぶ側が `try/except` で包むことになり、
**「確かめて届かないと分かった」と「確かめられなかった」が混ざる**。
だから `Reachability` という値にして返す。

一方 **401 や 403 は例外のままにする**。混ぜると、
トークンが切れているのに「相手にブロックされた」と報告することになり、
原因が違うのに同じ直しかたを試すはめになる。

### 「上限なし」を 0 と書かない

`quota` の `value` は、`type` が `limited` のときだけ返る（公式 OpenAPI 定義）。

| `type` | 意味 | `value` |
|---|---|---|
| `limited` | 上限がある | 返る |
| `none` | **無制限** | **省略される** |

無いものを 0 と読むと、**「無制限」が「使い切った」に化ける**。真逆である。
だから残数は `None`（上限なし）と数値を分け、**負の値も丸めない**
——丸めると「あと 0 通」と「12 通ぶん超過している」が同じ表示になる。

この判断は**記録にも照合にも一貫させた**。`results.json` の `remaining` は
無制限なら `null` で書き、`verify_notify.py` は `null` を**不合格にしない**。
片方だけ直しても、もう片方で 0 に化ける。

### 止める理由は全部集める

1つ見つけた時点で返すと、直して再実行したら次の理由で止まる、を繰り返させる。
`Gate` は `blocks`（止める理由）と `notes`（伝えるだけ）を分けて持ち、
**両方をまとめて返す**。分けているのは、「警告が出たから止まったのか」を
読み手が誤解しないため。

### 0 件でも送る

予定が無い日に何も送らないと、**通知が来ないことが「予定なし」なのか
「動いていない」のか、受け取る側から区別できない**。

枠は1通ぶん増えるが、**動いていることが分かる**ほうを取った。

### 件数が静かに減る経路を、全部ふさぐ

0 件が正常値でありうるので、**件数が減る失敗は「予定が無い日」と見分けが付かない**。

| 経路 | 対策 |
|---|---|
| 繰り返し予定が展開されない | `singleEvents=True` を必ず載せる |
| 終日予定を取りこぼす | `start.date` と `start.dateTime` の両方を見る |
| `summary` の無い予定を落とす | 代わりの見出しを入れて**残す** |
| `start` が未知の形の予定を落とす | 「時刻不明」として**残す** |
| 2ページ目を読まない | `nextPageToken` を**最後まで追う** |
| ページ上限で切る | 切らずに**落とす**（減ったことに気づく手段を残す） |

最後の1行がこの課題らしいところで、**上限に当たったら黙って切らずに例外にする**。
切ると「減った」という事実がどこにも残らない。

### 日付は外から渡す

`now` を引数で受け取る。実行時刻に依存させると、日付が変わった瞬間に挙動が変わり、
テストで境界を確かめられない。00:01 に走らせて当日ぶんを送る運用なので、
**境界のすぐ内側で動く**ことになる。

`vault_doctor` の `judge_tasks(tasks, now)` と同じ流儀に揃えた。

### 時刻のタイムゾーンを変換しない

`10:00` と出すのは、**カレンダーが返した時刻をそのまま**である。
利用者が画面で見ている時刻と一致するのが、この通知の目的だから。

問い合わせ窓（`timeMin` / `timeMax`）だけは JST 固定にしてある。
オフセットは RFC3339 で必須で、付け忘れると API 側の解釈になり、
**エラーは出ないまま1日ずれた予定が返る**。

### 課題9の送信を、そのまま使う

`push` の組み立て・再送キー・応答の読み取りは、課題9の `task9/send_push.py` を
**import して再利用している**。同じものを2度書かない。

理由は3つある。

1. **task9 を1行も変更しない**（読むだけの依存）。「連携済みのシステムに機能を
   追加する」という課題の要件どおり、既存に手を入れずに足せる
2. 二重実装にすると、**片方だけ直す事故**が起きる
3. 課題9のフィードバックで送信側が直れば、この課題にもそのまま効く
   ——**反映漏れが構造的に起きない**

### 照合が2つ増えた。だから限界も2つ増やした

課題9の `verify_push.py` の主題は「確認できないことを、確認できないと言う」だった。
課題10では照合の相手が2つ増えている。

| 照合の相手 | 何を言えるか |
|---|---|
| `/v2/bot/info` | 意図したチャネルを叩いた（課題9から） |
| `quota/consumption` | 送信対象として数えられた（課題9から） |
| `/v2/bot/profile/{userId}` | **いまも届く状態にある**（課題10） |
| `/v2/bot/profile/{userId}` の宛先 | **記録した宛先と、いまの `.env` の宛先が同じ**（課題10） |
| Google カレンダー | **対象日の件数が記録と合う**（課題10） |

**検査を足すと「確認した」の範囲が広がったように見える。そこがいちばん危ない。**
だから注記も2つ足した。

- カレンダーの照合が見ているのは「**いま**」の予定であって、送信した瞬間のものではない。
  送信後に予定を足し引きすれば、実装が正しくても不一致になる
- 送信前ガードが「届く」と答えたことは、**届いたことを意味しない**。
  `profile` が 200 を返した後にブロックされる余地は残る

### 自分の項目数を、自分で検査する（課題9からの宿題）

課題9の `check_docs.py` は最後に「照合 38 項目 / NG 0 件」と出していたが、
**その 38 が正しいかは誰も確かめていなかった**。検査を1つ足せば 39 になるのに、
README とスクリーンショットは 38 のまま残る。

課題9で入れなかった理由は「足すと 39 項目になり、**提出済みのスクショの 38 と
食い違う**」だった。順序として仕方がなかったが、そのまま忘れれば同じ穴が残る。
**課題10では最初から入れてある。**

いちばん間違えやすいのは**自分自身を数えるかどうか**である。この検査は最後に積まれるので、
積む直前の件数には自分が入っていない。+1 を忘れると README には常に1つ少ない数を書くことになり、
しかも**その状態で一致する**——ずれた物差しどうしが噛み合う。境界を1つずつテストで固定した。

## 公式ドキュメントで確認したこと（2026-08-20）

実装より先に調べた。**どれもエラーにならず、件数だけ静かに減る**種類の失敗である。

| 項目 | 分かったこと |
|---|---|
| `singleEvents` | 省くと**繰り返し予定が展開されない**。`orderBy=startTime` はこれが真のときだけ使える |
| `start` | 時刻付きは `dateTime`、**終日は `date`**。片方だけ見ると終日予定を丸ごと取りこぼす |
| `timeMin` / `timeMax` | RFC3339 で、**タイムゾーンのオフセットは必須** |
| `quota.value` | `type` が `limited` のときだけ返る |
| `profile` の必須項目 | `userId` と `displayName` だけ。`pictureUrl` / `statusMessage` / `language` は省略されうる（`language` は**利用者がプライバシーポリシーに同意していないと入らない**） |

## 実測でわかったこと

### テストが通っていることは、守られていることの証拠にならない

`tools/mutate.py` で 73 か所を1つずつ壊した。**素通りは合計 7 か所あった。**
どれもテストは全部緑だった状態で見つかっている。

#### 1. 部分一致が、意図しない場所で満たされていた（2026-08-20）

時刻の整形を確かめるテストが `assert "10:00" in text` だった。
だが整形前の値は `2026-08-21T10:00:00+09:00` で、**この中にも `10:00` は含まれる**。
つまり**整形を全部やめても通る**状態だった。

課題9の「2つの assert が両方とも、無関係な場所の文字列で満たされていた」と同じ原理である。
完全一致と、「含まれてはいけないものの否定」で塞いだ。

#### 2. 防壁を消しても、別の検査が肩代わりしていた（2026-08-20）

401 を例外にすることを確かめるテストで、`raise_for_line_error` を丸ごと消しても
テストが通ってしまった。**その先の「`userId` が無い」検査が別の例外を投げていた**ためである。
しかも `ApiError` は `LineError` のサブクラスなので、**例外の種類で見ても区別が付かない**。

本文を正常な形にして**防壁を1つだけにする**ことで塞いだ。
「例外が出た」ではなく「**この防壁が働いた**」を見るテストに変えたことになる。

#### 3. テストの日付が、実行した日と同じだった（2026-08-21）

対象日がカレンダーの問い合わせに渡ることを確かめるテストで、
**実装が対象日を捨てて `date.today()` で引くように壊しても通った**。
テストが使っていた日付が `2026-08-21` で、**その日が実行日そのものだった**ためである。

壊れた実装と正しい実装が、その日に限って同じ答えを返す。翌日には落ちるが、
**落ちたときにはもう「なぜ昨日は通ったのか」を調べることになる。**
送信側と照合側の**2か所**が同じ形で素通りしていた。

固定資産の日付を `2026-12-31` に変え、`timeMax` も併せて見るようにして塞いだ。
**「今日」を期待値に使わない。**

#### 4. 検査の数が、実行状況で変わっていた（2026-08-21）

自己検査（項目数の照合）を入れた直後に気づいた。`check_docs.py` は
`results.json` が無いとき「記録が無いので照合できない」の**1項目**を出し、
あるときは**6項目**を出していた。

つまり**実機で1回走らせるだけで、README が名乗るべき数字が 5 増える**。
自己検査そのものが「いつ数えたか」に依存していては、物差しにならない。

記録の有無にかかわらず**同じ項目が同じ数だけ並ぶ**ように直した。
記録が無いときは、同じ6項目が NG として出る。

#### 5. 「行数だけ」を見るテストが、崩れた本文を通した（2026-08-21）

予定名に改行が混ざると、本文の「1行 = 1件」という約束が崩れる。
そこを守るテストを書いたのだが、**畳む処理を外しても通った**。

数えていたのが「`- ` で始まる行の本数」だったためである。
続きの行は `- ` で始まらないので、**改行が残ったままでも「予定の行は1本」に見える**。
`verify_notify.py` の `count_event_lines` も同じ数え方をしているので、
照合側も気づけない。

畳んだ結果そのものを**完全一致**で押さえて塞いだ。
1つ目の素通り（`"10:00" in text`）とまったく同じ形で、
**「壊れていても満たされる assert」を1つの課題の中で2回書いた**ことになる。

### 実機の1回目で、この課題の主題がそのまま自分に起きた（2026-08-21）

`--dry-run` の1回目は「予定はありません。」と出した。**エラーも警告も1つも出ていない。**
ガードは通過し、チャネルの照合も通り、本文も組み上がっていた。

**だがその日、カレンダーには予定が2件あった。**

別の経路（カレンダーのコネクタ）で同じ日を数えたら 2 件で、食い違った。
そこで同じ資格情報で `calendars.get(calendarId="primary")` を叩いたら、原因が出た。

| | |
|---|---|
| スクリプトの token が見ていた primary | 開発用のアカウント |
| 予定を入れたカレンダー | **別のアカウント** |

同意画面で選んだアカウントが違っていた。**実装は1行も間違っていない。**
そのアカウントの 8月21日は、本当に空だったのである。

この課題はずっと「**0 件は正常値だから、件数が減る失敗と見分けが付かない**」と書いてきた。
その形が、実装ではなく**実行の確認**の側で出た。「予定が無い日」と
「別のカレンダーを読んでいる」は、出力の上で完全に同じ顔をする。

**片方の経路しか見ていなかったら、「実機で動いた」と結論して先へ進んでいた。**
課題4〜8で繰り返してきた「同じ応答の中で値を比べない」は、送信の照合だけでなく、
**自分の実行が何を見ているのか**にも要る。

### 終日予定の日付は、オフセットの付け方で1日ずれる（2026-08-21）

テスト用の終日予定を `2026-08-21T00:00:00+09:00` で作ったところ、
`start.date` が **`2026-08-20`** になった。**エラーは出ない。**
UTC に直すと前日の 15:00 になり、そこから日付だけが取られたためである。

作った側の話なので実装には関係しないが、**この課題が「静かにずれる」と書いた形が、
まったく別のクライアントで実際に起きた**。終日予定が `date`（時刻を持たない）で
表されるかぎり、どこでオフセットを畳むかで1日動く。机上の警戒ではない。

### 画面に出るものも、提出物である（2026-08-21）

スクリーンショットを撮り始めてすぐ、**プロンプトに絶対パスが写っている**ことに気づいた。
`C:` から始まるパスにはホームディレクトリ名が入り、そのまま画像に載る。

課題3で「`tools/mutate.py` から実ユーザー名を除く」と決め、課題9で「実行画面のパス表示を
リポジトリ相対にする」を入れた（`_display_path`）。それでも**プロンプトそのものは、
どちらの対策も通っていなかった**。コードから消しても、**コードの外に残っている**。

撮影用にプロンプトを短くして撮り直した。送信時に出る `記録: task10/line/results.json` が
相対で出ているのは前者の対策が効いているためで、そこは無事だった。
**対策が効いた場所と、効いていない場所が、同じ画面に並んでいた。**

### 記事を書く工程が、また1件釣り上げた（2026-08-21）

課題9でも同じことが起きた——記事に数字を書こうとして、README と実物の食い違いが出た。
今回釣れたのは数字ではなく、**主題そのものの根拠**だった。

発展アイデアの裏を取るために公式リファレンスの 404 の説明を読み直したら、こうあった。

> プロフィール情報を取得できませんでした。次のような理由が考えられます。
> 対象のユーザーIDが存在していない。**ユーザーがプロフィール情報の取得に同意していない。**
> ユーザーが対象のLINE公式アカウントを友だち追加していない。

こちらは「友だち追加されていないか、ブロックされています」と、**2つに決めつけて
利用者に見せていた**。とくに「同意していない」が効く。**友だちであっても 404 に
なりうる**ので、このガードは届く相手を止める側で間違えることがある。

止める側の誤りは、送ってしまう誤りより安全である。**だが安全であることと、
正しく説明していることは別だ。** 「ブロックされています」と読んだ利用者は、
相手に確認しに行くことになる。文言を公式の記述に合わせ、
**どれなのかは区別できない**と明記した。

なお、**ブロックされた相手に対してこの API が何を返すかは実測していない。**
公式の 404 の説明が挙げているのは上の3つで、ブロックが含まれるかまでは確認しきれなかった。

> **この記述自体を1度書き直している。** 最初は「第三者の記事に、ブロック後も取得できると
> 書かれている」と書いた。出典にあたったら**そんな記述は無かった**——検索結果の要約が
> 複数の情報源を混ぜていて、それを1つの記事に結びつけていた。
> **リポジトリ由来の数字は48項目すべて機械照合しているのに、外から持ってきた1行は
> 素通りしかけた。** 検査した範囲の外側は、検査していない。

確かめていないことは、確かめていないと書く——この課題がずっとやってきたことである。

### ガードが止まるところを、自分で再現する

届かない宛先を用意すれば、送信前ガードが止まることを実際に確かめられる。
**送信まで進まないので、通数は1通も消費しない。**

`.env` と同じ書式で、宛先だけを存在しない ID にしたファイルを作る
（`.env.*` は `.gitignore` に該当するので追跡されない）。

```bash
.venv/Scripts/python.exe task10/line/notify_schedule.py --env .env.demo
```

`[中止]` と `送信前の確認: 中止` が出て、**カレンダーの出力は1行も出ない**。
これがガードをカレンダーより前に置いた効果である——届かないと分かった相手のために、
Google の同意画面を開かせない。
