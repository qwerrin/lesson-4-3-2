# 課題10（Discord）— YouTube の新着を、二度送らず・取りこぼさずに流す

> ここまでAPI連携して作成したシステムのうち、2つのAPIを選び、それぞれに実用的な機能を
> 追加してみましょう。記事はAPIごとに1本、合計2本作成して提出してください。（要件の原文）

課題8で作った Discord への通知に、**課題6の YouTube というデータ源**と、
**どこまで送ったかの記憶**を足す。

> **状態（2026-08-23）**: 実装・テスト・実機・**スクリーンショットまで完了**。
> テスト **134 件**、わざと壊す検査 **95 か所すべて kill・素通り 0・置換先なし 0**、
> 文章とコードの照合 **56 項目・NG 0**。実機では3本を流し、
> 読み返しの照合 **24 項目すべて一致**。
> **撮ってから、この README に書いた**——課題7で「README に書いたのに存在しない
> 画像が2枚できた」を踏んでいるので、存在しないものを先に書かない。

## 「1回送って1回読み返す」では閉じない

課題8までの課題は、全部「1回動かして、1回読み返す」で閉じた。作ったものが
相手側に残るので、それを見に行けばよかった。

この課題で足すのは**繰り返し動くもの**である。そこで初めて出てくる問題がある。

> 1回だけ動くプログラムには「前回」が無い。
> 繰り返し動くプログラムは、前回の自分と話をしないといけない。

「新着を流す」と一言で言うが、**新着かどうかは、前回どこまで送ったかを
知らないと決められない**。だからこの課題で作るものは、実質2つある。

| | |
|---|---|
| 新着かどうかを決める**規則** | 何を「新しい」と呼ぶか |
| それを覚える**場所** | `state.json` |

## なぜ「動画の通知」なのか

課題8の記事に、発展アイデアとしてこう書いた。

> **他のサービスの更新をチャンネルに流す**（Notion や GitHub の変更を拾って投稿）
> — Discord をハブにしているコミュニティの運営者が、資料やロードマップを
> 更新したときに、全員に見に行ってもらうのが難しい時に使える。

自分で「実用的だ」と書いたものを、次の課題で実装する形にした。
題材が YouTube なのは、**課題6ですでに API キーを取ってある**のと、
毎晩1話ずつ動画を見て学習ノートを書く習慣が実際にあるためである。
説明が1行で済む——「見ている再生リストに動画が増えたら、Discord に届く」。

## 準備（この課題の利用者の手作業）

**増えるものは無い。** 課題6の `YOUTUBE_API_KEY` と、課題8の
`DISCORD_BOT_TOKEN` をそのまま使う。

| 資格情報 | 出どころ | この課題での用途 |
|---|---|---|
| `YOUTUBE_API_KEY` | 課題6（API キー） | 再生リストを読む |
| `DISCORD_BOT_TOKEN` | 課題8（Bot Token） | チャンネルへ投稿する |

Discord の bot には、投稿先チャンネルで**メッセージを送信**する権限が要る
（課題8で付けたもののまま）。

> **Message Content Intent は要らない。**
> 課題10の下調べで、bot が他人のメッセージ本文を読むにはこの権限が要ると
> 実測した。この課題は**送るだけ**なので関係がない。**要らない権限を
> 付けたままにしない。**

### 初回だけ通す手順

状態ファイルが空だと、**いま再生リストに入っているものが全部「新着」になる**。
100 本入っていれば 100 通が流れる。そこで初回は「送らずに覚える」を1度だけ通す。

```powershell
.venv\Scripts\python.exe task10\discord\relay_uploads.py `
  --handle '@GoogleDevelopers' --guild <サーバーID> --channel <チャンネルID> --init
```

`--init` は**状態ファイルが既にあると拒否する**。2回目に誤って叩くと、
まだ送っていない動画を「送信済み」にしてしまうためである。

## 実行

```powershell

.venv\Scripts\python.exe task10\discord\relay_uploads.py `
  --handle '@GoogleDevelopers' --guild <サーバーID> --channel <チャンネルID> --dry-run

# 実際に流す
.venv\Scripts\python.exe task10\discord\relay_uploads.py `
  --handle '@GoogleDevelopers' --guild <サーバーID> --channel <チャンネルID> `
  --json-out task10/discord/results.json
```

## 設計

### なぜ `search.list` を使わないのか

課題6は `search.list` を使った。新着を取るのにも使えるが、**繰り返し呼ぶ
用途には向かない**。公式のクォータ表にこう書いてある（2026-08-23 に確認）。

> The search.list and videos.insert methods have their own quota buckets.
> Each of these methods has a default daily limit of 100 per day.

| メソッド | コスト | 別枠の上限 |
|---|---|---|
| `search.list` | **100 units** | **1日100回**（10,000 ユニット枠とは別バケット） |
| `playlistItems.list` | 1 unit | 無し |
| `channels.list` | 1 unit | 無し |
| `videos.list` | 1 unit | 無し |

毎時ポーリングすると1日24回。`search` だと**1チャンネルだけで別枠の24%**を
使う。3チャンネル見れば 72%、4つで溢れる。しかもこれは**「ユニットを節約する」
では回避できない**——別枠の上限だからである（課題6の時点で分かっていた制約）。

`playlistItems.list` なら1回 1 unit で、この別枠にも入らない。

### 「新着」は2つある

最初は `snippet.publishedAt` を使うのを**バグ**だと思っていた。公式の文言が
はっきり分かれているためである（2026-08-23 に確認）。

> **snippet.publishedAt** — The date and time that the item was **added to the playlist**.
>
> **contentDetails.videoPublishedAt** — The date and time that the video was **published to YouTube**.

チャンネルのアップロード再生リストなら、2つはほぼ一致する。だから取り違えても
たいてい動く。ところが**キュレーションされた再生リスト**では話が変わる
——古い動画が今日追加されうるので、2つは何年もずれる。

そこで途中で考えを変えた。**「どちらが正しいか」ではなく「何を新着と呼ぶか」の
問題**だった。

| 何を流したいか | `--new-by` |
|---|---|
| 新しく**公開された**動画 | `published`（既定） |
| リストに新しく**入った**動画 | `added` |

片方に決め打つと、もう片方の使い方で**静かに取りこぼす**。公開が水位より古い
動画が今日追加された場合、`published` で見ていると二度と届かない。

### 並び順を意味に使わない

**公式は uploads 再生リストの順序を保証していない**（2026-08-23 に確認）。
だから「N番目＝N番目に新しい」は成り立たない。取得したあと、選んだ基準で
自分で並べ直す。

これは既出の罠と同じ形である。動画の再生リストで「N番目＝N話」がズレたときと、
記事の一覧で「先頭＝最新」と決め打って別の記事を編集しかけたとき。
**同じ原理の罠が、別の画面で戻ってくる。**

### 重複と取りこぼしのどちらに倒すか

「最後に送った動画の時刻」を覚えて、次はそれより新しいものを送る——素直に
考えるとこうなる。**これは同時刻の動画が2本あると必ず壊れる。**

| 比較 | 起きること |
|---|---|
| `時刻 > 水位` | 同時刻のもう1本を**永久に取りこぼす** |
| `時刻 >= 水位` | 送った1本を**毎回もう一度送る** |

だから**正本は videoId の集合**にした。水位は「どこまで遡れば十分か」を決める
ためだけに使う。集合が正本なら、比較を緩い側に倒しても重複しない。

**取りこぼす側に倒すと、取りこぼしたことに気づけない。** 通知が2回来たら人間が
気づくが、来なかったことには誰も気づけない。

### 記憶より広い窓を覗かない

覚える集合は無限には伸ばさない（既定 200 件）。状態ファイルが際限なく育つほうが
困るためである。ところが**遡る窓は最大 `max_pages × page_size` ＝ 250 件**で、
記憶より広い。こぼれた 50 件は「知らない動画」に見えるので、並びが崩れた日に
**古い動画が新着として流れる**。

これは書いている途中で気づいた。塞ぎ方を2つ重ねてある。

1. 覚える件数を窓に合わせる（`keep_for()` ＝ `max(200, max_pages × page_size)`）
2. `select_new` でも水位の床を効かせ、床より下は ID 集合に無くても送らない

2 が要るのは、1 だけだと**打ち切りが並び順に頼ったまま**だからである。
その並び順は公式が保証していない。

### 送信と記録のあいだの窓は消せない

「Discord へ送る」と「送ったと記録する」は別の操作なので、**あいだでプロセスが
死ぬ可能性は消せない**。決められるのはどちらに倒すかだけである。

| 倒し方 | 代償 |
|---|---|
| 記録してから送る | 送信に失敗した1本を**永久に落とす** |
| **送ってから記録する**（採用） | 死んだ位置によっては**1本だけ重複する** |

**1本送るごとに記録する。** まとめて最後に書くと、落ちたときの重複が最大で
全件になる。1本ずつなら最大1本で済む。

送信が失敗したらそこで止めて、後続を送らない。先へ進めてしまうと、失敗した1本
だけを後から入れ直す手段が無くなる（順番が崩れる）。

### 0 件でも送る、を今回は採らない

記事A（LINE の予定通知）では「**0 件でも送る**」と決めた。送らないと、通知が
来ない日が「予定が無い」のか「動いていない」のか区別できないためである。

**この課題では逆にした。** 新着が無い日は何も送らない。

| | 来ないことの意味 |
|---|---|
| 予定の通知（記事A） | **異常**。毎日来るはずのものが来ていない |
| 新着の通知（記事B） | **普通**。動画が増えていないだけ |

同じ人が逆の判断をしている。基準は「**沈黙が何を意味するか**」で、
沈黙が2つの意味を持つときだけ、必ず鳴らす側に倒す。

### 壊れた状態ファイルを、空として扱わない

`state.json` が読めなかったとき、`State.empty()` を返せばプログラムは動く。
**そして再生リストの全件がもう一度流れる。**

「読めなかった」と「まだ何も送っていない」は別のことなので、同じ値で表さない。
読めなければそこで止める。

保存も、同じ場所へ直接書かずに**別名で書いてから置き換える**。書き込み中に
落ちると中途半端な JSON が残り、それは次の実行から見て「壊れている」なので、
翌日から動かなくなる。

### 照合の物差しを、照合対象の中から取らない

投稿した本文は `playlistItems.list` の応答から組み立てた。同じ応答をもう一度
読んで比べても、**何も確かめたことにならない**——課題6で「トートロジー」として
踏んだ形である。

`verify_relay.py` は3つの**別々の源**から値を持ってきて突き合わせる。

| 源 | そこからしか分からないこと |
|---|---|
| Discord `messages/{id}` | **実際に載ったもの**。送信の応答ではない |
| YouTube `videos.list` | 本文を作った `playlistItems.list` と**別の口** |
| `state.json` | 次回に再送しない状態になっているか |

1本あたり **8 項目**を照合する。**合格したものも数えて出す**——落ちたものだけを
集めると「何項目を見たか」が分からず、検査を1つ落としても出力が静かに短くなる
だけになる。

### 他人が付けた文字列を、そのまま流さない

動画のタイトルは他人が書いたものである。そのまま Discord へ流すと、
`@everyone` を含むタイトルで**サーバー全員に通知が飛ぶ**。課題8の
`build_payload(..., allow_mentions=False)` をそのまま使って抑止している。

同じ理由で、タイトルは `html.unescape()` を通す。YouTube は `&` を `&amp;` に
して返すので、そのまま流すと人間が読む画面に `&amp;` が出る。
**課題7で Slack の同じ変換を踏んでいる**（保存時に変換し、表示時に戻す）。

照合側でも同じ変換を戻す。片方だけ戻していると、`&` を含むタイトルの日にだけ
**正しく動いているのに NG が出る**——そして「照合が厳しすぎる」と判断して
検査を緩める方向に倒れやすい。

### 課題8の送信を、そのまま使う

宛先の検証・伏せ字・メンション抑止・応答の読み取りは、課題8で 163 件のテストと
実機で確かめてある。ここで書き直すと、確かめ直しになる。

**資格情報は、それを使う関数が自分で取りに行く。** 呼ぶ側に読ませて渡す形に
していたら、送り先を差し替えたテストでも本物の Bot Token を要求してしまい、
テストが4件落ちた。課題8で `fetch_webhook` が「伏せ字を呼び出し側に任せない」
としたのと同じ理由である。

### 実行画面も提出物である

API キーは **URL のクエリに載る**。`HttpError` は失敗したリクエストの URI を
持っているので、例外をそのまま印字すると `...&key=<APIキー>` が画面に出る。
実行画面は public リポジトリに置くスクリーンショットになるため、
**印字した時点で公開事故**になる。

表に出す文字列は `youtube_auth.redact()` を通す。個々の呼び出しだけでなく、
`main` の最後の網でも通す——想定していない経路の例外がそのまま出れば同じことに
なるためである。

あわせて、スクリプトとして走らせたときだけ標準出力を UTF-8 に付け替えている。
**動画のタイトルには絵文字が入る。** Windows の既定のコンソールは cp932 で、
変換できない文字に当たると `UnicodeEncodeError` で落ちる——送信そのものは
成功しているのに、報告の途中で落ちる。しかも**絵文字の入った動画が来た日にしか
起きない**ので、手元では再現しない。

| `playlistItems.list` / `channels.list` / `videos.list` は 1 unit | 同上 |
| `snippet.publishedAt` は「**再生リストに追加された**時刻」 | [PlaylistItems](https://developers.google.com/youtube/v3/docs/playlistItems) |
| `contentDetails.videoPublishedAt` は「**YouTube に公開された**時刻」 | 同上 |
| `contentDetails.relatedPlaylists.uploads` がチャンネルのアップロード再生リスト | [Channels](https://developers.google.com/youtube/v3/docs/channels) |
| **uploads 再生リストの順序は保証されていない** | 同上（保証の記述が無い） |

## 実測でわかったこと

### テストが通っていることは、守られていることの証拠にならない

`tools/mutate.py` で実装を1か所ずつ壊し、テストが落ちるかを確かめた。
**最初の実行で 6 か所が素通りした**（当時 48 か所中）。どれも
「別の検査が先に拾うので、その行が無くても落ちない」形だった。

| 素通りした守り | なぜ落ちなかったか |
|---|---|
| `videoPublishedAt` が無いとき落とす | 空チェックが先に拾う。**メッセージの違いを見ていなかった** |
| タイムゾーンの無い時刻を弾く | **naive な時刻を渡すテストが1件も無かった** |
| UTC へ揃える | 検体が全部 `Z`。**ずれた時差を1度も渡していない** |
| 動画以外の項目を弾く | 検体から `videoId` も消していたので、空チェックが先に拾う |
| ページ跨ぎの重複を畳む | 辞書が勝手に畳む。**中身が同じ検体**だったので差が出ない |
| エラーから API キーを伏せる | **`main` のエラー経路を1件も通していなかった** |

**検体の作り方が粗いと、テストは通るのに何も守っていない。**
6 件とも、実装ではなくテストの側を直して塞いだ。

### 実装を直したら、壊し方も直さないといけない

途中で `--new-by` を足したとき、**壊し方の 5 件が「置換先なし」になった**。
`mutate.py` はこれを素通りと同じ失敗として扱うので気づけたが、
成功扱いにしていたら「**何も壊さずに穴ゼロ**」と出ていた。

### 単体で呼べない式は、壊しても素通りする

素通りが残った 4 件のうち 3 件は、「その計算を呼ぶ経路がテストに無い」ことが
原因だった。`keep = max(200, max_pages × page_size)` を `main` の中にベタ書き
していたので、確かめるには 250 件の偽データを組み立てる必要があった。

`keep_for()` と `floor_of()` として関数に出したら、1行で確かめられるようになった。
**テストしにくい形のまま置いておくと、テストしないまま置いておくことになる。**

`floor_of()` を作った理由はもう1つある。同じ式が2か所にベタ書きされていて、
**片方だけ壊してももう片方が同じ判定をしていた**ので、壊す検査が素通りしていた。
1つにまとめると、片方だけ余白を持つ（＝取ってきたのに捨てる／捨てるつもりのものを
送る）というねじれも起こせなくなる。

### 同じコマンドが、シェルによって別の意味になる（実機で発覚）

スクリーンショットを撮るために PowerShell で叩いたら、いきなり落ちた。

```
relay_uploads.py: error: argument --handle: expected one argument
```

**PowerShell では `@` が先頭に来ると演算子になる**（配列・スプラッティング）。
引用符で囲まずに `@GoogleDevelopers` と渡すと「変数 `$GoogleDevelopers` を
展開しろ」と読まれ、存在しないので**空に化ける**。だから `--handle` が
引数無しになった。

厄介なのは、**開発中に使っていた Git Bash では通る**ことである。`@` は普通の
文字なので、書いた本人の手元では一度も再現しない。README に載せた実行例は
**そのまま貼ると動かない**状態で、しかも誰も気づかない。

直し方は2つあって、どちらでも動く。

| 書き方 | なぜ動くか |
|---|---|
| `--handle '@GoogleDevelopers'` | 引用符で囲めば演算子にならない |
| `--handle GoogleDevelopers` | `normalize_handle()` が `@` を付け直す |

2つ目が効いたのは偶然ではない——「人は `@` を付けたり付けなかったりする」
という別の理由で入れた正規化が、そのままここを救った。

**同じ間違いを二度書けないように、`check_docs.py` に検査を足した**
——`--handle` の直後に引用符なしの `@` が来ていたら NG にする。
**踏んだ罠は、文章に書くだけでなく機械が見張る形にする。**

> **その検査を説明する文章で、検査に引っかかった。**
> ここに壊れる書き方をそのまま例として書いたら、`check_docs.py` が実際の
> 実行例として数えて NG を出した。**文章を足すだけで検査が悪化する**のは
> 既出の形（説明のつもりで書いた記法が、リンク検査に実リンクとして数えられた）。
> 例は記法を避けて書く。

### 偽物だけで固めたテストは、属性名の取り違えを通す（実機で発覚）

照合が実機で落ちた。**テストは 121 件すべて通っていた。**

```
AttributeError: 'Identity' object has no attribute 'id'
```

正しくは `identity.user_id` である。`compare()` と `read_video()` は偽物を渡して
固めてあったが、**`main()` の経路は1度も通していなかった**。

そして厄介なのは、**単体テストではこれが絶対に出ない**ことである。偽物を作るのは
自分なので、実装が `.id` を読んでいれば偽物にも `.id` を生やしてしまう。
**偽物は実装に似せて作られるので、実装の誤りごと写し取る。**

塞ぎ方は「本物の型を通す結合テスト」を1本置くこと。ネットワークは偽物のままでよい
——差し替えたいのは**通信**であって、**組み立て**ではない。

### 実行画面に自宅パスが出ていた（実機で発覚）

`--init` を2回目に叩いたときの拒否メッセージが、これを出していた。

```
エラー: 状態ファイルが既にあります: C:\Users\<名前>\Documents\...
```

`check_docs.py` は README とソースの自宅パスを検査している。**実行時の出力だけ
検査していなかった。** この画面はスクリーンショットになって public リポジトリに
載るので、写った時点で利用者の名前が公開される。

`shown_path()` を通し、リポジトリの外を指されたら**名前だけ**にした。
「相対にできないので絶対パス」に倒すと、**いちばん出したくない場合に
いちばん長いものが出る**。

> 検査で使う物差しにも同じ話がある。テストで `"C:"` のような綴りを探すと、
> 別の場所に置いた瞬間に素通りする。**その実行で使った絶対パスそのもの**が
> 画面に出ていないことを見る。

### 同じ名前のテストファイルは、片方が黙って別のものを検査する

`tools/check_docs.py` のテストを足したら、**リポジトリ全体のテストが収集で止まった**。

```
import file mismatch:
imported module 'test_check_docs' has this __file__ attribute:
  ...task10/discord/tests/test_check_docs.py
which is not the same as the test file we want to collect:
  ...task10/line/tests/test_check_docs.py
```

記事A（LINE 側）にも同名のテストファイルがある。pytest はテストディレクトリに
`__init__.py` が無いとファイル名をそのままモジュール名にするので、衝突する。

**名前を変えるだけでは足りなかった。** `check_docs` という**モジュール名も
両方で使っている**ためである。実際に確かめた。

```
1回目の import -> discord   （sys.path の先頭は discord/tools）
2回目の import -> discord   （sys.path の先頭を line/tools にしても同じ）
```

一度 `sys.modules` に入ると、`sys.path` を変えても2回目の `import` は
**同じオブジェクトを返す**。つまり記事A側のテストは、この課題のモジュールを
検査していた——実装がほぼ同じなので、**全部通ったまま**。

| | どう気づくか |
|---|---|
| テストファイルの名前衝突 | **エラーで止まる**ので気づける |
| モジュールの名前衝突 | **黙って通る** |

直し方は、テストファイル名を分けたうえで、**モジュールを名前ではなく
パスで読む**こと（`importlib.util.spec_from_file_location`）。あわせて
「読み込んだモジュールが自分のものか」を確かめるテストを1件足した。
これが無いと、将来この読み込みが名前解決に戻ったときに、残りのテストは
全部通ったまま別モジュールを検査する。

### heredoc の中のバックスラッシュは潰れる

`mutate.py` の壊し方を一括更新しようとして、`\n` を含む置換文字列が
**改行そのものに化けて**一致しなくなった。既知の罠で、以前にも踏んでいる。
ファイル編集はツール経由で行い、シェルの heredoc に通さないこと。
