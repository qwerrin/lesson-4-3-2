## 先に調べたこと（コードを書く前に）

課題2で、書き始めてから「Docs API が有効になっていない」「トークンの権限が足りない」に
当たった。どちらもコードの問題ではなく、**コードの外側にある状態**だった。
課題1のフィードバックにも「API からはコード以外の操作などが必要になってきます」とある。

そこで今回は、**必要な API・スコープ・返ってくる形を先に確定させてから**書く。
出典はインストール済みの `google-api-python-client` に同梱されている
Meet API v2 のディスカバリ定義（`meet.v2.json` / revision 20260421）と公式リファレンス。

### 使う API

| 項目 | 値 |
|---|---|
| API 名（有効化するもの） | **Google Meet API**（課題1の Drive、課題2の Docs とは別。改めて有効化が要る） |
| エンドポイント | `POST https://meet.googleapis.com/v2/spaces` |
| ライブラリでの呼び方 | `build("meet", "v2", credentials=...)` |

`meet.v2.json` は `googleapiclient/discovery_cache/documents/` に同梱されている。
つまり **ディスカバリの取得でネットワークに出なくても組める**。

### スコープ

`spaces` で使えるメソッドと、それぞれに必要なスコープ（定義から抜いた実測）。

| メソッド | HTTP | 必要なスコープ |
|---|---|---|
| `spaces.create` | `POST v2/spaces` | `meetings.space.created` |
| `spaces.get` | `GET v2/{+name}` | `meetings.space.created` / `meetings.space.readonly` / `meetings.space.settings` |
| `spaces.patch` | `PATCH v2/{+name}` | `meetings.space.created` / `meetings.space.settings` |
| `spaces.endActiveConference` | `POST v2/{+name}:endActiveConference` | `meetings.space.created` |

**要求するのは `meetings.space.created` だけにする。**

```
https://www.googleapis.com/auth/meetings.space.created
```

課題1で `drive.file` を選んだのと同じ理由で、いちばん狭いものを取る。
このスコープは「**自分のアプリが作ったスペースだけ**」に届く。作成にも読み返しにも
足りるので、これ以上は要らない。`readonly` は読むだけなので作成ができない。

**`token.json` は作り直しになる。** 課題2で取ったトークンは `documents` しか
持っていない。`common/google_auth.py` がそれを検出して同意画面を開き直すので、
手で消さなくてよい。

### 返ってくる形（`Space`）

| フィールド | 中身 | 書き込み |
|---|---|---|
| `name` | `spaces/{space}` 形式のスペース名。サーバが決める。大文字小文字を区別する | 不変 |
| `meetingUri` | 参加リンク。`https://meet.google.com/` ＋ `meetingCode` | 読み取り専用 |
| `meetingCode` | 会議コード。形式は `[a-z]+-[a-z]+-[a-z]+`（例 `abc-mnop-xyz`） | 読み取り専用 |
| `config` | `accessType`（`OPEN` / `TRUSTED` / `RESTRICTED`）など | 書ける |
| `activeConference` | いま開催中の会議。作った直後は無い | 読み取り専用 |

課題が言う「参加リンクの生成」は **`meetingUri`** のこと。作成の応答にそのまま入っている。

### 着手前に確かめられなかったこと（実機で解決した）

**個人の Google アカウントで `spaces.create` が通るかは、公式ドキュメントに明記が無かった。**
サービスアカウントで他人の代理をする場合は Workspace のドメイン全体の委任が要る、
とは書かれているが、今回のように本人が OAuth で同意する形についての記述が
見つからなかった。ドキュメントを探しても出てこないので、**実際に叩くまで分からない**
状態のまま設計に入った。

**結果（2026-08-14 実測）: 個人アカウントで通った。** Workspace は要らなかった。

通らなかった場合に備えて、**403 が返ったときに「API が有効化されていない」
「権限が足りない」「アカウントの種類が対応していない」を混ぜない**ようにしてある。
課題1で、権限エラーが 404 で返ってきて ID の打ち間違いにしか見えなかったのと同じ形を避けるため。
今回は使わずに済んだが、3番目はコードでも設定でも直せない種類の失敗なので、
起きたときに読み取れる形にしておく意味は残る。

## 照合する項目（実物を見る前に決めた）

課題1は MD5（中身のバイト列）、課題2は段落数（文書の構造）で照合した。
**相手の形が変われば、確かめたことになる項目も変わる。**

スペースには「中身」が無い。代わりに、返ってくる値の**あいだに規則がある**。

> `meetingUri`: `https://meet.google.com/` に `meetingCode` を続けたもの
> `meetingCode`: `[a-z]+-[a-z]+-[a-z]+`

この2つは別々のフィールドとして返ってくるのに、片方からもう片方が決まる。
つまり**突き合わせられる**。ここを軸にする。

| # | 照合する項目 | 見ているもの |
|---|---|---|
| 1 | スペース名が一致 | 読み返したのが本当にそのスペースか |
| 2 | 参加リンクが一致 | 作成時に返った `meetingUri` と、読み返した値が同じか |
| 3 | 会議コードが一致 | 同上（`meetingCode`） |
| 4 | 参加リンクが会議コードと整合 | `meetingUri` が `https://meet.google.com/` ＋ `meetingCode` になっているか |
| 5 | 会議コードの形が正しい | `[a-z]+-[a-z]+-[a-z]+`。リンクとして成立するか |
| 6 | アクセス種別が指定どおり | 送った `config.accessType` が反映されたか（**個人アカウントでは指定自体ができなかった**。下記参照） |
| 7 | 会議はまだ始まっていない | `activeConference` が無い。**スペースを作ることと会議が始まることは別** |

**4番が今回の要。** 2番と3番は「同じ値が返ってきた」しか言っていない。
サーバが両方おかしな値を返せば、2番と3番はどちらも一致する。
4番だけが、2つの値のあいだの規則を見ている。

**7番は「作成 ≠ 開催」を確かめる項目。** リンクができたことと、
会議が始まっていることは違う。ここを混ぜると「作れた」の意味が曖昧になる。

値が返ってこなかった項目は NG にする（課題1・課題2と同じ）。
既定値を入れると、照合できなかったケースが全部「一致」に化ける。

## 認証部分は共有した

課題1・課題2では認証まわりを課題ごとにコピーしていた。中身はほぼ同じで、
違ったのは例外の名前だけだった。課題2の振り返りに「課題3からは共有したい」と書いたので、
リポジトリのルートに `common/google_auth.py` を作ってそこに置いた。

```python
from common import google_auth

SCOPES = ("https://www.googleapis.com/auth/meetings.space.created",)

```

**`load_credentials` にスコープの既定値は持たせていない。** 課題ごとに違う値で、
間違えても「権限が足りないまま動いているように見える」形になるため、呼ぶ側に必ず書かせる。

課題1・課題2のコードは**そのまま残してある**。提出済み・採点中の成果物なので、
記事に書いた内容と実物がずれないようにするため。移行するのは採点が出てから。

**共有した時点で、共有モジュール専用のテストを書いた**（`common/tests/`・14件）。
課題1・課題2のトークン関連テストは、それぞれの課題のコピーを見ているだけで、
新しく切り出した `common/google_auth.py` は誰も見ていなかった。
共有物にテストが無いと、壊れたときに落ちるのは「使っている側の課題」で、
原因が共有物にあると分かりにくい。

## 実行方法

**すべてリポジトリのルート（`lesson-4-3-2/`）で実行する。**

```bash

```

アクセス種別を指定することもできる。

```bash

```

初回だけ既定のブラウザが開いて Google の同意画面が出る。課題2の `token.json` が

実測（2026-08-14）:

```
ミーティングのスペースを作成しました
  スペース名    : spaces/Lur6cy9YX1AB
  会議コード    : mwk-drid-pdr
  アクセス種別  : TRUSTED
  参加リンク    : https://meet.google.com/mwk-drid-pdr
```

**アクセス種別は指定していない。** ここに出ている `TRUSTED` は、送っていないのに
サーバが返してきた値＝アカウントの既定。指定した値が反映されたのではないので、
照合では「アクセス種別が一致」の項目を使っていない（指定していないものを
一致と言わせないため）。

スペース名・会議コードは実行ごとに変わる。**このページに出てくる値は全部この1回の
実行のもの**で、下の照合結果も同じスペースを指している。

### オプション

| オプション | 意味 |
|---|---|
| `--access-type` | `OPEN` / `TRUSTED` / `RESTRICTED`。未指定ならアカウントの既定に従う。**個人アカウントでは指定すると 403 になる**（「つまずいたところ」参照） |
| `--credentials` | OAuth クライアントの JSON（既定: `credentials.json`） |
| `--token` | トークンの保存先（既定: `token.json`） |

`ACCESS_TYPE_UNSPECIFIED` は**受け付けない**。「指定しない」という意味の値なので、
指定して既定になったのか未指定なのかが実行画面から読み取れなくなる。

## つまずいたところ

### 個人アカウントでは、作れるのに設定はできない

`spaces.create` は個人アカウントで通る。ところが `--access-type RESTRICTED` を
付けた途端に 403 になった。

```
応答: updateAccessType is not available to the user.
```

**作成そのものと、作成時に設定を指定することは、別の権限だった。**
スコープ（`meetings.space.created`）は足りている。API も有効になっている。
それでもこの項目だけ弾かれる。アカウントの種類で決まるので、コードでは直せない。

この結果、`config.accessType` を送る経路は個人アカウントでは使えない。
指定しなければアカウントの既定（今回は `TRUSTED`）で作られる。

### 自分で書いた案内に、自分で引っかかった

このとき最初に出た画面がこれだった。

```
操作が許可されませんでした（403）。
原因の候補が3つあります。
  1. Google Meet API が有効になっていない
  2. token.json の権限が足りない
  3. 使っている Google アカウントの種類が Meet API に対応していない
応答: updateAccessType is not available to the user.
```

**Google は項目名まで正確に教えてくれているのに、こちらが候補を3つ並べて埋めていた。**
このページの上のほうに「403 が返ったときに原因を混ぜない」と自分で書いたのに、
その通りになっていなかった。原因を並べることと、原因を伝えることは違う。

応答が具体的なときは、その具体的な内容を先に出す分岐を足した。

```
アクセス種別（config.accessType）は、このアカウントでは設定できません（403）。
--access-type を付けずに実行すれば、アカウントの既定のまま作成できます。
スペースの作成そのものは通ります。設定できる項目はアカウントの種類で決まるので、コードでは直せません。
応答: updateAccessType is not available to the user.
```

**テストでは出せなかった。** 偽の `service` に渡すエラー文面は自分で書くので、
「`updateAccessType is not available to the user.` という応答が来る」ことを
知らなければテストにも書けない。実物を叩いて初めて出てきた文字列だった。

### 最初は4か所が素通りした

| 素通りしたもの | 何が起きていたか |
|---|---|
| API 未有効化の案内を出さない | 分岐を消しても、汎用の 403 メッセージが原因候補として「API が有効になっていない」を並べているので「有効」の字が残った。**別の文章に当たって通っていた** |
| 権限不足の案内を出さない | 同じ形。汎用メッセージに「権限が足りない」が入っている |
| 403 の原因からアカウントの種類を落とす | その行を消しても、次の行の「別の**アカウント**で試す」に当たった |
| 会議コードの形を部分一致で見る | `fullmatch` を `search` にしても、正規表現に `^` と `$` があるのでほぼ同じ挙動。**壊しかたのほうが的外れ**だった |

上の3つはテストの側を締めて消した（実装は変えていない）。
**その分岐でしか出せない情報**で見分けるようにした。「有効」ではなく「ライブラリ」、
「権限」ではなく要求スコープそのもの、「アカウント」ではなく「アカウントの種類」。

4つめは挙動が変わらないので壊しかたの問題だが、1つだけ差が出るケースがあった。
`$` は**文字列末尾の改行の手前にも一致する**ので、`abc-mnop-xyz\n` は
`search` なら通り `fullmatch` なら落ちる。端末からコードを写すと改行が付いてくるので、
そのケースをテストに足した。
