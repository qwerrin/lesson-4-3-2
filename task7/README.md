# 課題7 Slack API — 指定のチャンネルにメッセージを投稿する

> Slack API を利用して、指定のチャンネルにメッセージを投稿するスクリプトを作成してください。
>
> 【ヒント】認証トークンとスコープを設定が大切です。

## 作ったもの

| ファイル | 役割 |
|---|---|
| `task7/post_message.py` | `chat.postMessage` で投稿し、`chat.getPermalink` でリンクを取る |
| `task7/verify_message.py` | `conversations.history` で読み直して突き合わせる（**読むだけ**） |
| `common/slack_auth.py` | Bot Token の読み込みと `auth.test` による確認。課題をまたいで使う |
| `task7/tools/mutate.py` | 実装を1か所ずつ壊して、テストが落ちることを確認する |
| `task7/tools/check_docs.py` | この README とコードを機械照合する |

## 使い方

リポジトリのルートで実行する。トークンは環境変数で渡す（コマンドライン引数は履歴と `ps` に残るため）。

```powershell
$env:SLACK_BOT_TOKEN = "xoxb-..."

.venv\Scripts\python.exe task7\post_message.py --channel C0BQFU7STLM `
    --text "課題7: Slack API の投稿テスト & 読み返し照合 <chat.postMessage>" `
    --json-out task7/results.json

.venv\Scripts\python.exe task7\verify_message.py --results task7/results.json `
    --channel C0BQFU7STLM `
    --expect-text "課題7: Slack API の投稿テスト & 読み返し照合 <chat.postMessage>"
```

**チャンネルは ID（`C` で始まる値）で指定する。** `chat.postMessage` は名前でも受け付けるが、
読み返しに使う `conversations.history` は ID しか受け付けない。両方に同じ値を渡せる形にしておくと、
「投稿したチャンネル」と「読み返したチャンネル」がずれない。チャンネル名は変わるが ID は変わらない、
という実務上の理由もある。ID は Slack のチャンネル詳細の一番下に出ている。

## 設計 — 読み返しの物差しをどこから取るか

投稿が成功しても、それは「API が `ok` を返した」までしか意味しない。本当にそのチャンネルへ、
狙った本文が、こちらの Bot の名前で載ったのかは、別のところから読み直さないと閉じない。

**同じ応答の中で値どうしを比べるのはトートロジーで、何も確かめていない。**
そこで物差しを3つとも応答の外から取る。

| 何を確かめるか | 物差しの出どころ |
|---|---|
| チャンネル・本文 | **人間がコマンドラインで渡す**（`--channel` / `--expect-text`） |
| タイムスタンプ | 投稿時に記録した値と、読み返した値を突き合わせる |
| 投稿者 | **`auth.test`**（`conversations.history` とは別のエンドポイント）が答えた `user_id` |

3つ目が効くのは、投稿の応答と読み返しの応答という同じ系統の中だけで比べていないから。
実測では `conversations.history` が返した `user` が `auth.test` の `user_id` と一致した
（どちらも `U0BQ48E7E3H`）。

## Slack 側の準備（全部この課題の利用者の手作業）

API キーやトークンを AI に入力させることはできないので、ここは必ず人が通る工程になる。

1. ワークスペースを作る（<https://slack.com/get-started>）
2. <https://api.slack.com/apps> → 「Create an App」→ **「Blank app」を選んで「Continue」**
   - **かつての「From scratch」は「Blank app」に名前が変わっている**（2026-08-17 に実物で確認）。
     公式のクイックスタートは「from a manifest」を案内していて、この選択肢に触れていない
   - 「Starter app」を選ぶと、スラッシュコマンドとイベント購読が最初から入った状態で作られる。
     **スコープを自分で付ける工程が消える**ので、この課題では選ばない
3. **OAuth & Permissions** → 「ボットトークンのスコープ」に2つ追加する
   （「ユーザートークンのスコープ」ではない）

   | スコープ | 使うメソッド |
   |---|---|
   | `chat:write` | `chat.postMessage` |
   | `channels:history` | `conversations.history` |

4. 「Install to <ワークスペース名>」でインストールし、**Bot User OAuth Token**（`xoxb-` で始まる）を取る
5. **投稿先のチャンネルに Bot を招待する** — チャンネルで `/invite @<アプリ名>`、
   またはチャンネル名 → 「インテグレーション」→「アプリを追加する」

**5 を飛ばすと `not_in_channel` で落ちる。** スコープを付けただけでは投稿できない。

## 実測でわかったこと

### 権限（スコープ）と所属（チャンネル参加）は別物

招待前に実行すると、スコープは足りているのに投稿できない。

```
スコープ: chat:write / channels:history
Slack API がエラーを返しました: not_in_channel
Bot がチャンネルに参加していません。Slack のチャンネルで `/invite @<アプリ名>` を送って招待してください。
```

エラーの案内で**スコープの話をしない**ようにしてある。相手が `not_in_channel` と名指しで
答えているところに原因候補を並べると、合っている設定を疑わせて遠回りさせる。

### 送った文字列は、そのままの形では返ってこない

Slack は `&` `<` `>` を制御文字として扱い、HTML エンティティに変換して保存する。

```
送った本文 : '課題7: Slack API の投稿テスト & 読み返し照合 <chat.postMessage>'
返った本文 : '課題7: Slack API の投稿テスト &amp; 読み返し照合 &lt;chat.postMessage&gt;'
そのまま一致?      : False
変換を掛けたら一致? : True
```

課題5（Gmail）で件名が RFC 2047 で返ってきたのと同じ形の罠で、**変換を解かずに比べると永久に不一致**になる。
`post_message.escape_for_slack()` を通してから突き合わせている。

- **`&` を最初に置換する。** 逆にすると `<` → `&lt;` で作られた `&` を次の段でもう一度拾い、
  `&amp;lt;` になる
- **照合を「どちらでも通す」形にしない。** 生の値でも変換後でも一致とみなすと、
  照合そのものが何も確かめなくなる
- **和文だけで試すと永久に気づけない。** この課題の実行例に `&` と `<>` をわざと入れているのはそのため

### 画面で一致して見えても、保存されている値とは限らない

`06-slack.png` の Slack の画面には、`課題7: Slack API の投稿テスト & 読み返し照合 <chat.postMessage>` と
**送ったとおりの形**で表示されている。一方 `conversations.history` で読むと `&amp;` `&lt;` `&gt;` が返る。
**Slack は保存では変換し、表示ではデコードして見せている。**

つまり**画面を目で見て一致していても、保存されている形は分からない**。
「投稿先を開いて、狙いどおりに載っているかまで見る」だけでは届かない範囲がここにあり、
API で読み直す照合が別に要る理由になっている。逆に、API の値だけを見ていると
「利用者にどう見えるか」が分からない。**両方見て初めて閉じる。**

### `conversations.history` が返すのは「その ts のメッセージ」ではない

1件だけ読み直すには `oldest=<ts>` + `inclusive=true` + `limit=1` を渡す。ただしこれは
「**その ts 以降の最初の1件**」であって、狙ったメッセージが消えていれば次のメッセージが1件返る。

- `inclusive` を落とすと**自分自身が結果に入らない**。エラーにはならず 0 件になるだけなので、
  指定を消したことに気づけない
- 件数だけ見て「取れた」と判断すると、別のメッセージを相手に照合することになる。
  **返ってきた `ts` が渡した `ts` と同じか**を照合の項目にしてある

課題6の「`videos.list` は存在しない ID を黙って落として 200 を返す」と同じ形である。

### タイムスタンプは識別子であって時刻ではない

`1786915517.894839` を `float` にすると倍精度で表しきれず、末尾が変わって別のメッセージを指す。
文字列のまま持ち回り、結果ファイルにも文字列で書く。

### 付与済みスコープは応答本文に入らない

課題4（Zoom）はトークンの応答に `scope` が入っていたので、足りない権限をその場で名指しできた。
Slack は本文に入らず、HTTP ヘッダ `x-oauth-scopes` に入る。
**公式のメソッドリファレンス（`auth.test` / `chat.postMessage` / `conversations.history`）には
この記載がない。** 実測では返ってきたが、書かれていない以上「返る」ことを前提にはできない。

そこで「足りなければ例外」ではなく、判定結果を返す形にした。
**読めなかったときは、要求したスコープを全部「足りない」側に入れて返す。**
呼び出し側が `if check.missing:` と書いても安全側に落ちる。
空にすると「確認できていない」が「足りている」に化ける。

そのうえで、**読めなかっただけでは投稿を止めない**。ヘッダが返らない環境で課題そのものが
実行できなくなるため。ただし画面には「確認できません」と必ず出す。

### `auth.test` はスコープを要求しない

権限の設定が済んでいなくてもトークンの有効性だけは確認できる。最初の1回をここに置くと、
`invalid_auth`（トークンが違う）と `missing_scope`（権限が足りない）を分けて報告できる。

**プレフィックス（`xoxb-`）の検査は形式しか見ていない。**
User Token（`xoxp-`）でも `auth.test` は成功するが `bot_id` を返さないので、そちらで性質を見る。
User Token は**投稿自体は通ってしまう**ため、弾かないと「アプリが投稿した」つもりで
本人名義の投稿ができあがる。

### 送っていない項目が応答に付いてくる

`text` だけ送っても、読み返すと `blocks` / `bot_profile` / `app_id` / `team` が付いている。

```
返ってきたメッセージのキー: ['app_id', 'blocks', 'bot_id', 'bot_profile', 'team', 'text', 'ts', 'type', 'user']
```

照合は必要な項目だけを名指しで見る。応答全体を比べる形にすると、こちらが関与していない項目の
変化で落ちるようになる。

## わざと壊す（ミューテーション）

```powershell
.venv\Scripts\python.exe task7\tools\mutate.py
```

**74か所すべてでテストが落ちた（素通り0件・置換先が見つからないもの0件）。**

### 方式を変えた — 壊す道具は、壊れたまま止まる

課題2〜6の `mutate.py` は実ファイルを書き換えて1件ごとに戻していた。これは課題4で実際に事故っている
（強制終了すると `atexit` が走らず、`if False:` が残ったまま止まった）。控えを取る・復旧手順を書く、
という手当てをしても「壊す道具は壊れたまま止まる」という性質そのものは消えない。

そこで**リポジトリを丸ごと一時ディレクトリへ写して、写した側だけを壊す**形にした。
成果物のファイルは1バイトも触らないので、途中で落ちても事故が起きない。
**復旧手順が要らなくなる＝復旧手順が間違っている可能性も消える。**

### 最初の実行で9件が素通りした

8件は同じ形だった。**「例外が出ること」は見ているが「正しい理由で落ちること」を見ていない。**

`ok=False` を返す偽の応答に `ts` を入れ忘れていたため、`ok` の検査を丸ごと消しても
*次の* 検査（`ts` が無い）で落ちて、テストは緑のままだった。
入力を「他の条件は全部満たしたうえで、狙った1点だけ違う」形に直して塞いだ。

残る1件は種類が違った。`_read_scopes()` の先頭に置いていた `if not headers: return None` は、
**外しても結果が1つも変わらなかった**（空の dict ならループが回らず下の `return None` に落ち、
`None` なら `.items()` が `AttributeError` を出して同じところへ落ちる）。
テストを何件足しても kill できない。**守っているつもりの行が、実は何もしていない**という指摘なので、
ガードごと削除した。

| 画面で確かめるもの | どこを見るか |
|---|---|
| チャンネル | アドレスバーの `C0BQFU7STLM` |
| 本文 | メッセージ本文 |

**リンクを開くと、アドレスバーは `app.slack.com/client/<チームID>/<チャンネルID>` に変わる。**
permalink はリダイレクトするので、開いたあとのアドレスバーに permalink そのものは残らない。
確認できるのはチャンネル ID の一致までである。

**同じ本文が2件並んでいる。** 実行を2回したためで、照合したのは下の `06:25` のほう。
`ts`（`1786915517.894839`）はエポック秒なので、ローカル時刻に直すと `2026-08-17 06:25:17` になり、
画面のどの投稿を指しているかが確定する。時刻の計算に使わないだけで、**人が画面と突き合わせる
手がかりにはなる**。「記事に出す実行結果の ID は1種類に揃える」という約束はここでも同じで、
画面に複数写るときは**どれを指しているかを本文で名指しする**。

**スクリーンショットはシークレットウィンドウで撮る。** ブックマークバーもアカウント画像も出ないので、
公開物に個人情報が写る事故が構造的に起きない。
